# 0001. Rust core compiled to WASM, thin JS-facing adapter

## Context

Limen needs to run entirely in the browser (no server, no network calls at runtime) while
guaranteeing that "native" (CLI/test) trial results and "browser" (WASM) trial results are
literally the same computation, not two independently-maintained implementations that merely
intend to agree. The domain logic involved -- a bundled tokenizer, five deterministic selection
strategies, manifest validation, metrics computation, and canonical JSON/SHA-256 digesting -- is
non-trivial enough that reimplementing it twice (once in Rust for tests/tooling, once in
TypeScript for the browser) would create an ongoing risk of silent behavioral drift between the
two, especially under future changes.

## Decision

All domain logic lives entirely in `crates/limen-core`, a pure Rust crate with zero WASM or
browser dependencies: the tokenizer (`tokenizer.rs`), the strategy trait and its five
implementations (`strategy/`), manifest validation (`validate.rs`), metrics (`metrics.rs`), and
canonicalization/digesting (`canonical.rs`). `crates/limen-wasm` is a deliberately thin adapter:
every exported function does exactly three things -- call into `limen-core`, convert the result to
a JSON string, and cross the `wasm-bindgen` boundary. It contains no parallel tokenizer, selector,
evaluator, validator, or digester logic; see that crate's `src/lib.rs` module doc comment, which
states this explicitly as an invariant. `web/src/wasm/engine.ts` is the sole point in the
TypeScript codebase that imports the generated WASM bindings, and it only parses the JSON strings
the engine returns -- it does not reimplement any decision logic.

Concretely, both `limen-wasm`'s `run_trial` export and `limen-core`'s own golden-fixture generation
and regression tests call the exact same native function, `limen_core::run_trial` (see
`crates/limen-core/src/result.rs`): one function, two callers. This makes "the WASM adapter and
the native tests run the same logic" true by construction, not by convention.

## Consequences

- **Testable, not just asserted, parity.** Because both paths converge on one Rust function, the
  claim "native and browser results are the same implementation" is provable rather than aspirational:
  `crates/limen-wasm/tests/wasm_parity.rs` runs the real compiled `wasm32-unknown-unknown` artifact
  (via `wasm-pack test --node`, not a mock) against all 75 golden-fixture trials
  (3 scenarios x 5 strategies x 5 budget tiers) and asserts byte-identical canonical JSON and
  identical `result_digest`s versus the native fixtures generated by `limen-core`'s own examples.
  This is the concrete evidence behind the parity claim, not just an architectural intention.
- **A future strategy/metric change automatically stays in sync everywhere.** Editing
  `limen-core` and rebuilding `limen-wasm` is the only step needed; there is no second file to
  remember to update.
- **The browser bundle pays a WASM-loading cost.** `limen-wasm`'s compiled `.wasm` binary
  (~560 KB uncompressed as built for this foundation) is loaded and instantiated once at startup
  (see `web/src/wasm/engine.ts`'s `ensureEngineReady`), rather than the app being pure,
  instantly-parseable JavaScript.
- **No panic may cross the WASM boundary.** Because the JS side cannot meaningfully recover from an
  unhandled Rust panic (a trapped WebAssembly instruction poisons the module), `limen-wasm` relies
  entirely on the Result-based discipline already present throughout `limen-core` (no
  `unwrap`/`expect`/`panic!` on any reachable decision or artifact-construction path) rather than
  `catch_unwind`, which is unavailable on the pinned stable toolchain for `wasm32-unknown-unknown`
  (see `crates/limen-wasm/src/lib.rs`'s module doc comment for the full reasoning).

## Alternatives considered

- **Reimplement the engine in TypeScript, no WASM.** Rejected: this is exactly the "duplicated
  selection logic in TypeScript" this project explicitly avoids, and would make native/browser
  parity a matter of careful manual synchronization (and re-testing both sides) rather than a
  structural guarantee.
- **A thicker `limen-wasm` adapter that also does some display/formatting logic in Rust.**
  Rejected: display concerns (DOM rendering, ARIA labeling, timelines) belong in `web/src` where
  they can be tested with Vitest/Playwright against real DOM APIs; pushing them into
  `limen-wasm` would blur the "one real implementation per concern" boundary this ADR exists to
  establish, for no parity benefit.
- **Run the Rust engine server-side instead of compiling to WASM.** Rejected: this project's
  product requirement is a fully offline, static, same-origin app with no runtime network
  request of any kind; a server would violate that directly.
